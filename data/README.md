# The two baked leaderboards

Every build bakes a board into the bundle, but **not the same one** — which of
the two depends on whether that build can reach the Worker at runtime. The
choice is made by `leaderboardSnapshotPlugin` in `vite.config.ts`, keyed on
`VITE_LEADERBOARD_URL`.

Both files are **committed**. Neither is a build artifact.

---

## `leaderboard-snapshot.json` — the real board

Pulled off the live Worker by `pnpm leaderboard:snapshot` (and refreshed
automatically by the Vite plugin when it is more than ten minutes stale).

Baked into builds that **do** have an endpoint (CrazyGames, web, GameDistribution,
Playgama…). There it is only the bottom rung of the offline ladder — live fetch →
per-device cache → this file — i.e. what a player sees when the fetch fails on a
device with no cache of its own yet. ~1.7 kB gzipped.

## `leaderboard-seed.json` — the synthetic board

Generated by `pnpm leaderboard:seed`, and marked `"synthetic": true` with its
generator named in `source` so nothing downstream mistakes it for measured data.

Baked into builds that **cannot** reach the Worker — **Poki** and **YouTube
Playables**. Those platforms forbid external runtime requests, so those builds
neither fetch a board nor post a score: whatever is baked in is the board those
players see, permanently.

**Why not bake the real board there?** Because it cannot grow from those
platforms. It would freeze at however many players existed the day the package
was cut — seven at the time of writing, mostly test accounts — and every Poki
player's result screen would read "#1 of 7" forever. The synthetic board instead
gives a rank that *moves* as the player progresses and sits roughly where a
comparable player would really sit.

Its shape is a casual-game funnel, asserted by the generator rather than
hand-written, so a tweak that breaks the intended curve fails loudly:

|               |                                     |
|---------------|-------------------------------------|
| population    | 257,114                             |
| mode          | stage 3–4 (where most players stop) |
| stages 1–2    | ~8%                                 |
| stages 10–20  | ~18%                                |
| past stage 40 | ~4%                                 |
| top player    | stage 159                           |
| published cut | stage 132                           |

It is deterministic — a fixed PRNG seed — so re-running produces a
byte-identical file and it never churns the repo.

---

## Gotcha

`pnpm leaderboard:snapshot` writes **only** the real board and can never
overwrite the seed. That separation is deliberate: the two lived in one file at
first, and `build:poki`'s snapshot refresh clobbered the seeded board on every
build.

For the same reason `build:poki` and `build:youtube` no longer run a snapshot
refresh — they do not consume that file, so it was a Worker round trip for
nothing. They make **no network call at build time at all**.
